## 1. 출발점: 왜 다시 고민했나

- 원래 아이디어: 농수산물 도소매 시세가 자주 급변하니 **계산해서 예측해 주자**
- 원래 수익 구조: 식봄에 구매를 연결하고 연결 수수료를 받자
- 걸린 점: **예측 대상은 공영도매시장 시세인데, 연결 대상은 식봄 판매가**라 둘이 잘 이어지지 않는 느낌
- 그래서 "도소매 사이트로 연결 대상을 바꿀까?" → "그 사이트가 수수료를 낼까?" → "애초에 사장님은 어디서 사고, 원가를 어떻게 계산할까?"로 질문이 이어짐

**슬라이드 한 줄**: 예측은 도매 시세, 연결은 식봄. 이 연결고리가 약하다는 데서 출발했다.

## 2. VOC 수집 방법: 크롤링이 가능한가

| 구분 | 내용 | 위험도 |
|---|---|---|
| 기술 | 대부분 회원 공개 글이라 로그인 · 등급이 필요. 기술적으로는 가능 | 중 |
| 약관 | 네이버 약관이 자동 수집 금지. 계정 정지 · 카페 강퇴 위험 | 상 |
| 법 | 회원 전용 글을 대량으로 모으면 민사 책임이 생길 수 있음 (2022년 대법원 여기어때 사건: 형사는 무죄, 민사는 별개) | 중~상 |
| 개인정보 | 닉네임 · 가게 위치 · 매출이 섞여 있음 | 중 |
| 실익 | BM에 필요한 건 반복되는 고민 10~20개. 수만 건은 필요 없음 | — |

검토한 다른 방법

| 방법 | 결과 |
|---|---|
| 네이버 검색 API (카페글 검색) | 2026년 7월 31일부터 신규 키는 **네이버 클라우드 NAVER API HUB**에서만 발급. 지금은 한시 무료, 월 775,000건. 클라우드 가입 부담으로 보류 |
| 직접 검색 + 시트에 한 줄 요약 | 가능 (보조) |
| 공개 자료 (aT 외식업 경기동향, 소상공인 실태조사) | 수치 근거로 사용 |
| 설문 · 인터뷰 | "돈을 낼 건가"를 직접 물을 수 있어 BM 검증에 가장 강함 (다음 단계) |
| **캡처 → AI가 읽고 분류** | 카페 글 복사가 막혀 있어 **최종 선택** |

**슬라이드 한 줄**: 긁어 오지 않고, 읽고 캡처했다. 분류는 AI가, 판단은 사람이.

## 6. 연결 대상: 사장님이 쓰는 곳 vs 구조에 맞는 도소매 사이트

### 6-1. 두 선택지 비교

| 기준 | A. 사장님이 실제로 쓰는 곳 (식봄 등) | B. 우리 구조에 맞는 도소매 사이트 하나 |
|---|---|---|
| 사장님이 누를까? | **이미 쓰는 곳이라 바로 누름** | 새로 가입해야 함. 최소 주문량 · 결제 방식이 낯섦 |
| 예측과의 연결 | 도매 시세 → 판매가가 뒤따르는지 보여 줘야 함 | 경락가와 직접 이어짐 |
| 판매처의 협조 | 필요 없음 (검색 링크만 걸면 됨) | 필요 없음. 다만 사장님이 쓰지 않으면 의미 없음 |
| 중립성 | 여러 판매처를 같이 보여 주면 유지 | 한 곳만 밀면 "광고 앱"으로 보임 |
| 근거 | 캡처에서 식봄 사용이 많이 보임 (VOC로 비율 확인 예정) | 없음 |

### 6-2. 추천: A — 사장님이 쓰는 곳에 연결, 대신 연결 이유를 바꾼다

1. **식봄은 "도소매가 아닌 곳"이 아니다.** 식봄은 식자재 유통사 · 도매상이 사장님에게 파는 **온라인 장터**입니다. 즉 도매상이 파는 창구입니다.
2. **도매 시세는 "먼저 움직이는 신호", 식봄 판매가는 "뒤따라 움직이는 값"**으로 연결합니다.
   - "대구 도매시장에서 양배추가 오르기 시작했어요. 식봄 판매가는 보통 며칠 뒤 따라 오르니 지금 사 두세요."
   - 이러면 예측(도매)과 연결(식봄)이 자연스럽게 이어집니다.
   - **가정**: 식봄 판매가가 실제로 며칠 늦게 따라 오르는지는 아직 확인 전입니다. 지금 `foodspring.py`가 6시간마다 식봄 가격을 받고 있으니, 2~3주 쌓아서 도매 시세와 비교하면 확인할 수 있습니다.
3. **한 곳만 연결하지 않는다.** 식봄 + 대형마트(참가격) + 쿠팡 · 네이버 쇼핑을 같이 보여 주고, 사장님이 고르게 합니다. 지금 화면 구조(식봄 상품 + 대형마트 판매가)와도 맞습니다.

### 6-3. 판매처가 링크 연결에 협조할 이유가 있나?

- **링크만 걸 때는 판매처의 허락이나 협조가 필요 없습니다.** 검색 결과 링크는 누구나 걸 수 있습니다. 문제는 "수수료를 낼 이유"입니다.
- 판매처가 연결 수수료를 내기 어려운 이유

| 이유 | 설명 |
|---|---|
| 살피는 "기다리기"를 말함 | 판매처 입장에서는 "지금 사지 마세요"라고 말하는 앱에 돈을 낼 이유가 없음 |
| 마진이 얇음 | 식자재 유통은 이익률이 낮아 수수료 몇 %도 부담 |
| 손님은 이미 있음 | 단골 위주 장사. 새 손님 몇 명 때문에 제휴하지 않음 |
| 협상력 없음 | 사용자가 거의 없는 초기 앱과는 계약하지 않음 |

- 그래서 **판매처가 원해서 돈을 낼 만한 것**을 따로 만듭니다. 판매처가 원하는 건 "손님 소개"가 아니라 **"미리 알 수 있는 주문량"**입니다.
- 이번 기업 트랙과의 연결: **CJ프레시웨이가 식봄 운영사(마켓보로)의 최대주주**입니다. "살피의 원가 · 수요 데이터로 CJ프레시웨이가 대구 수요를 미리 파악한다"는 제안이 가능합니다.

### 6-4. 수익 구조 (정리안)

| 순서 | 누가 돈을 내나 | 무엇에 | 판매처 협조 |
|---|---|---|---|
| ① 핵심 | 사장님 | 유료 구독: 영수증 분석 · 메뉴 원가율 · 구매 시점 알림 | 필요 없음 |
| ② 바로 가능 | 판매처 (자동) | 쿠팡 파트너스 · 네이버 쇼핑 커넥트처럼 **이미 열려 있는 제휴 프로그램**. "제휴 링크" 표시 필수 | 필요 없음 |
| ③ 확장 | 도매상 · 식자재 유통사 (CJ프레시웨이 등) | **지역 수요 예측 리포트** ("다음 주 대구 분식집 양파 수요 ↑", 가게 개별 정보 제외) | 판매처가 원해서 삼 |
| ④ 확장 | 도매상 | **공동구매**: "지금 사기" 시점에 주문을 모아 한꺼번에 넘기고 대량 할인 | 판매처가 원해서 참여 |
| 보조 | 공공 | 소상공인 디지털 전환 지원사업 바우처 | — |

**슬라이드 한 줄**: 연결은 사장님이 쓰는 곳에, 수수료가 아니라 "미리 알 수 있는 주문량"을 판다.

### 7-1. 지금 구조

- 제미나이 대화 하나가 **도구 12개**를 모두 들고, 시스템 프롬프트 하나에 **질문 유형 5개(A~E)** + 브랜드 말투 규칙이 다 들어 있음 ([agent.py](../../salpi_agent/agent.py))
- 영수증 읽기([receipts.py](../../salpi_agent/receipts.py))는 이미 따로 떨어져 있음
- 아침 브리핑도 사장님이 요청할 때마다 대화 모델이 새로 만듦

### 7-2. 병목은 어디인가

| 병목 | 원인 | 서브에이전트로 풀리나? | 해결 |
|---|---|---|---|
| 도구 고르기 실수 · 긴 답 | 도구 12개 + 규칙이 한 프롬프트에 몰림 | **풀림** | 담당별로 도구 3~6개, 규칙도 그 담당 것만 |
| 답이 느림 | 도구를 하나 부르고 → 결과 받고 → 또 부르는 순서 진행 | 일부 | 섞인 질문은 담당 둘을 **동시에** 부름 |
| 무료 API 한도 | 대화 · 영수증 읽기가 같은 키 · 같은 한도를 씀 | **오히려 나빠질 수 있음** (모델 호출이 늘어남) | 버튼 질문은 모델 없이 규칙으로 나누기, 브리핑은 미리 계산 |
| 첫 실행 2~3분 | 4주치 시세를 그때 받음 | 안 풀림 (데이터 문제) | 매일 새벽에 미리 받아 두기 |

> 주의: 에이전트를 나누면 모델 호출 수가 늘어 **무료 한도를 더 빨리 씁니다.** 그래서 "나누기"와 "모델을 안 쓰고 미리 계산하기"를 같이 해야 병목이 줄어듭니다.

### 7-3. 제안 구조

```
사장님 질문
   │
   ▼
[안내 담당] ── 버튼 질문은 규칙으로 바로 보냄 (모델 호출 없음)
   │            자유 질문만 가벼운 모델(flash-lite)로 분류
   ├──▶ [시세 담당]      시세 흐름 · 7일 예측 · 지금 사기/기다리기 · 날씨 · 행사 · 공휴일
   ├──▶ [원가 담당]      메뉴 원가 계산 · 우리 가게 원가율 · 가격 조정 · 대체 재료
   └──▶ [가게 준비 담당] 내일 판매량 · 발주량
                         (섞인 질문은 두 담당을 동시에 부르고 합침)

[미리 계산 작업] 매일 새벽: 시세 받기 → 예측 → 아침 브리핑 문장 → 알림톡 문구 (대화 모델과 분리)
[영수증 읽기]    사진 → 품목 · 가격 (지금처럼 따로, 한도를 덜 쓰는 모델 우선)
[VOC 분석]       카페 캡처 → 페인포인트 · 원가 계산 방식 분류 (서비스 밖, 팀 리서치용)
```

| 담당 | 도구 (지금 [agent.py](../../salpi_agent/agent.py) 기준) | 지금 프롬프트의 어느 부분 |
|---|---|---|
| 안내 | 없음 (분류만) | — |
| 시세 | `get_market_overview` · `get_item_price_trend` · `forecast_item_price` · `recommend_buy_now` · `get_weather_summary` · `get_daegu_events` · `get_upcoming_holidays` · `list_supported_items` | A · C |
| 원가 | `list_standard_menus` · `calc_menu_margin` · `get_store_cost_ratio` | B · E |
| 가게 준비 | `forecast_store_demand` (+ 필요하면 `recommend_buy_now`) | D |

- 공통 규칙(숫자는 도구 결과만, 판매처 권하지 않기, 살피 말투)은 모든 담당에 똑같이 넣음
- 말투만 고치는 담당을 따로 두지 않음 (호출이 한 번 더 늘어서 느려짐)

### 7-4. 나누는 순서 (작게 시작)

1. **브리핑 · 알림톡을 미리 계산 작업으로 분리**: 효과가 가장 크고 위험이 가장 작음
2. **버튼 질문 3개를 규칙으로 바로 보내기**: 모델 호출 1번 절약
3. 원가 담당 분리 → 시세 담당 분리 → 마지막에 안내 담당

### 7-5. 서브에이전트 주의점

나누면 좋아지는 점만큼 새로 생기는 문제도 있습니다. 나누기 전에 아래를 확인합니다.

| # | 주의점 | 무엇이 문제인가 | 대응 |
|---|---|---|---|
| 1 | **모델 호출이 늘어남** | 안내 1번 + 담당 1~2번으로 질문 하나에 호출이 2~3배. 제미나이 무료 한도(하루 · 분당)를 더 빨리 씀 | 버튼 질문은 규칙으로 분류, 브리핑 · 알림톡은 새벽에 미리 계산, 안내는 가벼운 모델 |
| 2 | **오히려 느려질 수 있음** | 안내 → 담당으로 단계가 하나 늘어남. 바쁜 시간에는 단계마다 기다림 | 섞인 질문만 담당 둘을 동시에 부름. 단순 질문은 담당 하나로 바로 |
| 3 | **잘못된 담당으로 보냄** | "양파 올라서 김치찌개 남아?"처럼 시세 + 원가가 섞인 질문을 한쪽에만 보내면 반쪽 답 | 분류 결과를 "여러 개 가능"으로. 애매하면 두 담당 다 부름. 분류 실패 시 지금의 통합 살피로 넘김 |
| 4 | **숫자가 서로 다름** | 시세 담당은 도매 경락가, 원가 담당은 영수증 · 참고 단가를 씀. 합치면 같은 양파 값이 두 개 나옴 | 답마다 기준(도매 · 영수증 · 참고 단가)을 꼭 붙임. 지금 규칙 E "시장 시세 기준과 섞지 않는다"를 합치는 단계에도 적용 |
| 5 | **말투 · 원칙이 담당마다 달라짐** | 공통 규칙(숫자는 도구 결과만, 판매처 권하지 않기, "기다리기", 살피 말투)을 담당마다 복사하면 하나만 고쳐지고 나머지는 옛 규칙으로 남음 | 공통 규칙은 **한 곳에만** 두고 모든 담당이 불러 씀 (`brand/SKILL.md`를 지금처럼 한 번만 읽기) |
| 6 | **대화 기억이 끊김** | 지금은 대화 하나라 앞 질문을 기억함. 나누면 "그럼 그건 언제 사?"에서 "그거"를 담당이 모름 | 안내 담당이 최근 대화 몇 줄을 담당에게 같이 넘김. 화면이 대화 기록을 들고 있는 지금 구조 유지 |
| 7 | **답을 합칠 때 또 호출** | 담당 둘의 답을 모델로 다시 다듬으면 호출이 하나 더 늘어남 | 합치기는 모델 없이 순서대로 붙이기 (시세 → 원가 → 준비). 전체 10줄 규칙은 담당마다 나눠 가짐 |
| 8 | **실행 시간 제한** | Vercel 서버는 요청 하나에 쓸 수 있는 시간이 정해져 있음. 단계가 늘면 시간 초과 위험 | 담당 호출에 각각 시간 제한을 두고, 넘으면 "잠시 후 다시" 안내. 동시 호출로 전체 시간 줄이기 |
| 9 | **고장 원인 찾기가 어려움** | 틀린 답이 나왔을 때 안내 실수인지, 담당 실수인지, 도구 문제인지 구분이 안 됨 | 질문마다 "어느 담당 · 어떤 도구 · 걸린 시간"을 기록 |
| 10 | **시험할 것이 늘어남** | 담당마다 따로 확인해야 하고, 섞인 질문도 따로 확인해야 함 | 기본 질문 3개 + 섞인 질문 3개를 고정 시험 질문으로 두고, 바꿀 때마다 돌려 봄 |
| 11 | **바쁠 때 갈아타기** | 지금은 바쁘면 다음 모델로 넘어가는 장치가 대화 하나에만 있음 | 담당마다 같은 갈아타기 장치를 쓰도록 공통 함수로 |
| 12 | **너무 일찍 나누기** | 시연 단계에서 구조만 복잡해지고 체감 차이는 작을 수 있음 | 7-4 순서대로 하나씩. 각 단계 후 **속도 · 한도 사용량 · 답 정확도**를 재 보고 좋아졌을 때만 다음 단계 |

**나누지 않는 게 나은 경우**
- 하루 질문 수가 적고 무료 한도에 걸린 적이 없을 때
- 지금 답이 도구를 잘 고르고 있을 때 (고르기 실수가 병목이 아님)
- 발표 · 시연 직전 (구조 변경은 시연 뒤로)

**판단 기준**: 나누기 전과 후에 같은 시험 질문으로 **① 답이 나오는 시간 ② 질문당 모델 호출 수 ③ 도구를 맞게 고른 비율**을 비교하고, 셋 중 둘 이상 좋아졌을 때만 유지합니다.

**슬라이드 한 줄**: 살피 하나가 다 하던 일을, 시세 · 원가 · 가게 준비 담당으로 나누고, 매일 같은 계산은 새벽에 미리 해 둔다. 단, 나눌 때마다 속도 · 호출 수 · 정확도를 재서 좋아졌을 때만 유지한다.
