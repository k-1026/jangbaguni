# 예측 기록 · 7일 뒤 자동 채점 · 식봄 판매가 기록 · 적중률 보기 (11/12)

> 무엇: 살피가 **실제 화면에 낸 예측**을 매일 저장하고, 7일 뒤 실제 가격과 비교해 **스스로 채점**한다. 같은 길로 식봄 판매가도 매일 쌓는다
> 왜: 과거 되돌려 채점([1112_forecast_backtest_results.md](1112_forecast_backtest_results.md))은 "그날 예측했다면?"을 다시 계산한 것. **실제로 사장님께 보여 준 예측이 맞았는지**는 기록해 둬야만 알 수 있다
> 계획 문서: [1112_forecast_validation_agent.md](1112_forecast_validation_agent.md) 3 · 4절 (검증 에이전트의 ① 기록 ② 채점 단계)

## 0. 한 줄 요약

| 기능 | 하는 일 | 저장 위치 |
|---|---|---|
| **예측 기록** | 그날 화면에 나간 7일 예측을 그대로 저장 (하루 약 40줄) | Supabase `forecast_log` |
| **7일 뒤 자동 채점** | 기준 날짜에서 7일이 지나면 실제 가격과 비교해 방향 적중 · 범위 적중을 채움 | 같은 표의 채점 칸 |
| **식봄 판매가 기록** | 재료별 식봄 상품 판매가를 하루 한 번 저장 (하루 약 60줄) | Supabase `price_snapshots` |
| **적중률 보기** | 최근 몇 주 채점 결과를 종류별 · 품목별로 요약 | `GET /api/forecast-score` |

- 따로 예약 실행을 걸지 않아도 **그날 처음 누가 사이트에 들어오면** 자동으로 저장 · 채점됨
- 11/12 첫 저장 확인: 예측 40줄 (야채 15 · 과일 10 · 육류 7 · 수산물 8), 식봄 판매가 58줄
- **첫 채점은 11/18~19** (11/11 시세 기준 예측 + 7일)

## 1. 어떻게 돌아가나

```
[사이트 첫 방문 (그날 처음)]
   │  대시보드 계산 (/api/overview · /api/meat-seafood) ── 이미 하던 계산, 시세 API를 더 부르지 않음
   ▼
[뒤에서 한 번] ──▶ ① 예측 기록: 오늘 예측 40줄 저장 (이미 있으면 건너뜀)
                ──▶ ② 채점: 기준 날짜 + 7일이 지난 예측을 대시보드가 받아 둔 4~5주 시세와 비교
[식봄 상품 화면 첫 계산]
                ──▶ ③ 식봄 판매가 저장 (재료별 상품 4개씩)
[누구나]
   GET /api/forecast-score ──▶ ④ 최근 4주 적중률
```

| 구분 | 내용 |
|---|---|
| 코드 | `salpi_agent/forecast_log.py` (저장 · 채점 · 요약), `salpi_agent/server.py` (하루 한 번 실행 · API) |
| 표 | `supabase/schema.sql` F절 (`forecast_log` · `price_snapshots`) — 11/12 Supabase에 만듦 |
| 하루 한 번 | 서버가 그날 이미 했는지 기억 → 두 번 저장하지 않음. 같은 날 · 품목은 **처음 저장한 값을 바꾸지 않음** |
| 실패하면 | Supabase 키가 없거나 연결이 안 되면 저장만 건너뛰고 화면은 그대로. 다음 요청 때 다시 시도 |

## 2. 예측 기록 (`forecast_log`)

| 칸 | 뜻 | 예 (11/12 양파) |
|---|---|---|
| `run_date` · `item` | 저장한 날 · 재료 (둘이 합쳐 한 줄) | 2026-11-12 · 양파 |
| `kind` | 야채 · 과일 · 수산물 · 육류 | 야채 |
| `base_date` · `base_price` · `unit` | 예측의 기준이 된 마지막 시세 날짜 · 가격 · 단위 | 11-11 · 1,060원 · kg |
| `expected_change_pct` | 다음 7일 예상 변화율 | −2.1% |
| `range_low` · `range_high` | 예상 범위 | 954 ~ 1,121원 |
| `direction` | up · flat · down (±2% 기준, 화면 문구와 같음) | down ("떨어질 가능성") |
| `factors` | 이유별 영향 (화면 "이렇게 본 이유" 그대로) | 반입량 −1.3 · 4주 평균과의 차이 −0.8 |
| `formula_version` | 예측 공식 버전 (`analysis.FORMULA_VERSION`) | 2026-11-12 |

- 저장하는 품목 = 화면에 보이는 품목. **제철이 아니라 숨긴 과일**(4주 거래일 8일 미만)은 저장하지 않음
- **공식을 바꾸면 `FORMULA_VERSION` 날짜를 바꿀 것** → 버전별로 따로 채점해 고친 공식이 실제로 나아졌는지 비교

## 3. 7일 뒤 자동 채점

| 단계 | 기준 |
|---|---|
| 채점 대상 | `base_date` 가 7일 이상 지났고 아직 채점 안 한 줄 |
| 실제 가격 | `base_date + 7일` 이후 **첫 시세 날짜** (사흘 안). 휴장 · 미조사로 없으면 다음에 다시 |
| `actual_change_pct` | (실제 가격 ÷ 기준 가격 − 1) × 100 |
| `direction_hit` | 실제 변화율을 같은 ±2% 기준으로 나눴을 때 예측 방향과 같으면 맞음 |
| `in_range` | 실제 가격이 예상 범위(`range_low` ~ `range_high`) 안이면 맞음 |

- 기준은 과거 되돌려 채점(`backtest.py`)과 **같음** → 과거 성적과 실제 성적을 바로 비교할 수 있음
- 시세 API를 더 부르지 않고, 대시보드가 이미 받아 둔 4~5주 기록에서 찾음

## 4. 식봄 판매가 기록 (`price_snapshots`)

| 칸 | 뜻 |
|---|---|
| `snap_date` · `source` · `url` | 저장한 날 · '식봄' · 상품 주소 (셋이 합쳐 한 줄) |
| `item` · `product_name` | 살피 재료 이름 · 식봄 상품 이름 |
| `sale_price` · `original_price` | 판매가 · 할인 전 가격 |
| `kg` · `price_per_kg` | 상품 무게(이름 · 규격에서 읽음) · kg당 가격 |

- 쓰임: **"식봄 판매가가 도매 시세를 며칠 늦게 따라가나"** 비교 (BM의 "도매가 = 먼저 움직이는 신호" 근거, [VOC 분석](../bm/1112_voc_analysis.md) 7절 "내가 산 값이 비싼지" 기능)
- 2~3주 쌓인 뒤 비교 시작
- 주의: 식봄 검색 결과(기본 배송 지역) 기준이라 대구 판매자 가격과 다를 수 있음. 상품 무게를 못 읽으면 kg당 가격이 빔

## 5. 적중률 보기 (`GET /api/forecast-score?weeks=4`)

```json
{
  "weeks": 4, "since": "2026-10-15", "formula_version": "2026-11-12",
  "all":   {"n": 120, "direction_hit_pct": 45.0, "in_range_pct": 70.0, "opposite_pct": 25.0},
  "kinds": {"야채": {…}, "과일": {…}, "수산물": {…}, "육류": {…}},
  "items": {"양파": {"n": 5, "direction_hit_pct": 60.0, …, "kind": "야채"}, …}
}
```
(숫자는 모양을 보여 주는 예시. 11/12 현재 채점된 예측은 0개)

| 값 | 뜻 |
|---|---|
| `n` | 채점된 예측 수 |
| `direction_hit_pct` | 오를 · 유지 · 내릴 문구가 맞은 비율 |
| `in_range_pct` | 실제 가격이 예상 범위 안이었던 비율 (목표 70% → 80%, [1108 문서](1108_forecast_formula_v2.md)) |
| `opposite_pct` | 오른다 했는데 내렸거나 그 반대 (사장님께 가장 손해) |

- `weeks` 는 1 ~ 26. 결과는 30분 동안 보관 (자주 불러도 Supabase를 계속 읽지 않음)
- 다음 단계: 채점이 4주 쌓이면 재료 페이지에 **"지난 4주 이 재료 예측: 방향 ○/○번 맞음"** 표시 ([검증 에이전트 계획](1112_forecast_validation_agent.md) 6절)

## 6. 운영 · 주의

| 항목 | 내용 |
|---|---|
| 데이터 보기 | Supabase 대시보드 → **Table Editor** → `forecast_log` · `price_snapshots` |
| 바로 실행 | `POST /api/jobs/daily` → 저장 · 채점 · 식봄 판매가를 바로 하고 줄 수를 돌려줌 (예: `{"recorded": 40, "scored": 0, "shop_rows": 58}`) |
| **빠지는 날** | 아무도 사이트에 안 들어온 날은 기록이 빠짐. 매일 꼭 남기려면 GitHub Actions 예약 실행으로 `POST /api/jobs/daily` 를 매일 아침 부르면 됨 (평일 저녁 배포처럼) |
| Vercel | 기존 `SUPABASE_URL` · `SUPABASE_SECRET_KEY` 그대로 씀 (새 키 없음). 서버가 잠들면 뒤에서 하던 저장이 끊길 수 있음 → 다음 방문 때 다시 시도 |
| 열려 있는 주소 | `POST /api/jobs/daily` 는 누구나 부를 수 있음. 같은 날 다시 불러도 중복 저장은 안 되지만 시세 계산을 다시 하므로, 예약 실행을 붙일 때 비밀 값으로 막는 것을 검토 |
| 개인정보 | 저장하는 것은 시세 · 예측 · 공개 상품 가격뿐 (사장님 · 가게 정보 없음) |
